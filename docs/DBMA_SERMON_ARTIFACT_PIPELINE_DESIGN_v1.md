## 1. 진단 — ❌ 다섯 개는 같은 뿌리에서 나온다

매트릭스의 ❌를 하나씩 채우는 것은 답이 아니다. 다음 다섯 행은 **하나의 구조적
공백**의 다른 증상이다.

| 매트릭스 행 | 전제 조건 |
|---|---|
| 예화 생성 | 설교가 있어야 예화를 붙인다 |
| 적용/소그룹 질문 | 설교가 있어야 질문을 뽑는다 |
| 강단 전달 모드 | 설교 원고가 **다시 열려야** 한다 |
| 설교 재활용 | "한 편의 설교"가 입력이다 |
| 시리즈/캘린더 | 설교가 **시간축에 쌓여야** 한다 |

공백은 이것이다:

> **DBMA에서 생성된 설교는 저장되지 않는다.**

`ui/pages/sermon_draft.py`의 설교 상태는 전부 `st.session_state["sermon_draft_state"]`
에만 있고(:217, :269, :326, :389), 파이프라인의 종착점은 `st.download_button`(:467)이다.
브라우저를 닫으면 사라진다.

### 1.1 함께 사라지는 것이 더 중요하다

`state["candidates"]` — 개요 생성에 사용된 검색 결과(`RankedCandidate` 20건)가 같이
증발한다. 이것은 단순 캐시가 아니라 **그 설교의 근거 목록**이다. 함께 사라지는 것:

- 인용 근거 (어느 자료의 어느 TSU에서 나왔는가)
- `judge_sermon_groundedness()`의 입력 (`retrieved_candidates`)
- `doctrine_check()` 결과 (`state["doctrine_report"]`)
- 감사 추적 — 매트릭스에서 **"압도적 우위"**로 적은 바로 그 항목

즉 DBMA의 최대 강점(출처 승인·감사 추적)이 **문서 계층에만 있고 설교 계층에는
없다.** Pulpit AI의 제품 전체가 "one sermon → a week of content"인데, DBMA에는
그 "one sermon"이 객체로 존재하지 않는다.

### 1.2 결론

기능 5개를 각각 만들 것이 아니라, **설교를 1급 객체로 영속화하는 계층 하나**를
두면 나머지는 그 객체의 파생물이 된다.

## 2. 설계 원칙

1. **모방하지 않는다.** 경쟁사가 LLM으로 지어내는 것을 DBMA는 근거로 만든다.
   같은 기능을 열등하게 따라가면 영원히 뒤진다.
2. **ADR-001 불가침.** 새 검색 경로·병렬 랭킹을 만들지 않는다. 모든 검색은
   기존 `QueryProcessor.process()`를 통과하고, 필요한 선별은 **사후 필터**로 한다
   (`sermon_draft.py`가 이미 `_CANDIDATE_K=20`으로 쓰는 패턴).
3. **기존 자산 재사용.** `SermonRecord`, `save_sermon_record()`,
   `sermon_corpus/analyzer/`, `judge_sermon_groundedness()`, `doctrine_filter`,
   `identity_registry` 패턴이 이미 있다. 새로 짓지 않는다.
4. **못 하는 것은 못 한다고 적는다.** §7 참조.

## 3. 계층 구조

```
                    ┌──────────────────────────────┐
  설교문 작성  ───▶ │   SermonArtifact (신규)       │
  (기존 3단계)      │   식별자 + 원고 + 근거 + 판정  │
                    └──────────────┬───────────────┘
                                   │  (같은 객체를 입력으로)
         ┌────────────┬────────────┼────────────┬────────────┐
         ▼            ▼            ▼            ▼            ▼
      예화 검색    적용·질문     강단 원고     재활용        시리즈
     (근거 기반)   (생성+검증)   (렌더링만)   (텍스트)     (시간축)
         │            │            │            │            │
         └────────────┴────────────┴────────────┴────────────┘
                                   │
                                   ▼
                    ┌──────────────────────────────┐
                    │  설교 코퍼스 (기존 2,782건)    │◀─ 되먹임
                    │  문체 참고 · 통계 · 중복 회피   │
                    └──────────────────────────────┘
```

핵심은 화살표가 **한 객체에서 갈라진다**는 것이다. 각 파생물이 독립적으로
설교를 재구성하지 않는다.

## 4. SermonArtifact — 데이터 설계

기존 `SermonRecord`(title/date/scripture/body)는 **과거 설교 수집용**이라 근거를
담지 못한다. 생성물 전용 레코드를 둔다.

```jsonc
{
  "sermon_id": "SRM-20260915-a3f2c1",      // 식별자 (identity_registry 패턴)
  "created_at": "2026-09-15T14:02:11",
  "scripture_and_theme": "로마서 5:1-5, 고난 중의 소망",
  "sermon_format": "주제설교",              // SERMON_FORMATS

  "outline":  { "title": "...", "introduction": "...",
                "points": ["..."], "conclusion": "..." },
  "expanded": { "0": "...", "1": "..." },   // 대지별 본문

  // ── 근거 (현재 증발하는 부분) ──────────────────────────
  "evidence": {
    "candidate_tsu_ids": ["TSU-ROM-...chunk_00222", "..."],
    "retrieval": { "k": 20, "query_id": "sermon-draft" }
  },

  // ── 판정 (현재 증발하는 부분) ──────────────────────────
  "doctrine_report":  { "passed": true, "warnings": [], "flagged_categories": [] },
  "groundedness":     { "score": 4.0, "rationale": "...",
                        "judge_model": "...", "prompt_version": "v1" },

  // ── 생성 재현 정보 ────────────────────────────────────
  "generation": { "gen_model": "llama3.1:8b", "temperature": 0.3,
                  "style_files": ["..."], "build_commit": "..." },

  "derivations": { "illustrations": [], "applications": [],
                   "questions": [], "repurpose": {} }
}
```

**설계 판단**

- `candidate_tsu_ids`만 저장하고 본문은 저장하지 않는다 — TSU 데이터셋이 정본이고
  중복 저장은 드리프트 원인이 된다. 조회 시 `tsu_id`로 되찾는다.
- `groundedness`를 **저장**한다. 현재 judge는 배치 평가용으로만 쓰이고 UI 설교에는
  붙지 않는다. 저장하면 "이 설교의 근거 충족도 4.0/5"를 목회자에게 보여줄 수 있다 —
  경쟁사 어디에도 없는 화면이다.
- `build_commit`을 넣는다. 문서 계층의 `tsu_manifest.json`이 하는 일과 같다 —
  설교 계층에도 감사 추적을 확장한다.

**저장 위치:** `data/sermon_artifacts/{sermon_id}.json` + 인덱스 `index.jsonl`
(`data/` 하위는 `.gitignore` 대상 — 개인 설교 원고가 커밋되지 않는다).

## 5. 기능별 실현 방법

### 5.1 예화 — ❌ 를 ✅**우위**로 전환 (최우선 차별화)

> **절대 규칙 (HQ 지시, 2026-09-15)**
> **예화는 절대 생성하지 않는다. 없으면 없는 대로 설교 원고를 신앙양심대로
> 작성한다.**
>
> 이 규칙은 설계 선택이 아니라 제약이다. 아래 모든 내용은 이 규칙 안에서만
> 유효하며, 어떤 이유로도 예외를 두지 않는다:
> - 검색 결과가 0건일 때 **생성으로 폴백하지 않는다.** 0건은 오류가 아니라
>   **정상 종료 상태**이며 화면에도 그렇게 표시한다("해당 대지에 쓸 수 있는
>   예화가 자료에 없습니다").
> - "예화 자리가 비어 보인다"는 이유로 채우지 않는다. 예화 없는 설교는
>   결함이 아니다.
> - 지어낸 예화는 목회자가 회중 앞에서 **사실로 전달하게 되므로**, 채팅
>   답변의 오류와 피해의 성격이 다르다. 되돌릴 수 없다.

**경쟁사는 LLM이 예화를 지어낸다.** 출처가 없고, 사실 여부를 확인할 수 없으며,
목회자가 강단에서 인용하기 위험하다.

**DBMA는 검색한다.** 방금 적재한 스펄전 MTP 2권(5,238 TSU)이 예화의 보고이며,
2026-09-15 `doc_type` 작업으로 **`설교`로 분류**되었다.

```
설교 대지 텍스트
  → QueryProcessor.process(대지 + 본문, k=30)     # ADR-001 준수, 기존 경로
  → 사후 필터: TSU.document_id → registry.doc_type == "설교"
       (TSU 레코드에 doc_type 필드가 없으므로 registry 조인으로 판정 — 읽기 전용)
  → 상위 3건을 [출처·저자·신뢰도]와 함께 제시
  → 목회자가 선택 → artifact.derivations.illustrations 에 tsu_id로 기록
```

**이것이 doc_type 작업이 필요했던 진짜 이유다.** 분류가 없으면 주석·사전에서
예화를 긁어온다.

한계: 현재 설교 코퍼스가 영어(스펄전)다. 한국어 예화는 목회자 본인의 과거 설교가
쌓이면서(§5.6 되먹임) 채워진다. **그때까지는 검색 결과가 비는 경우가 많을 것이며,
그것이 정상이다** — 빈 결과를 생성으로 메우지 않는다.

#### 선행 조치 완료 (2026-09-15)

예화 기능을 만들기 전에 **이미 있는 생성 경로가 예화를 지어내고 있었다**.
`core/generation.py::_EXPANSION_STYLE_GUIDANCE["주제설교"]`가
*"목회적 적용과 예화는 그 근거에서 자연스럽게 도출되게 하라"*로 **예화를 명시적으로
요구**하고 있었다.

더 심각한 것은 보호의 배치가 거꾸로였다는 점이다:

| 경로 | 적용되던 지시문 | 강도 |
|---|---|---|
| Chat / Research | `_GROUNDING_DIRECTIVE` (:377, :382) | 강함 — "자료에 없는 사실·인명·연도·장절을 추가하지 마라", "부족하면 거기서 멈춰라" |
| **설교 원고** | `_QUALITY_DIRECTIVE` (:591, :716) | 약함 — "지어내지 말고" 한 구절 |

강단에 올라가는 원고가 가장 약하게 보호되고 있었다. 조치:

- `_NO_FABRICATED_ILLUSTRATION_DIRECTIVE` 신설 — 개요·확장 **두 프롬프트 모두**에 배선
- `_EXPANSION_STYLE_GUIDANCE`에서 예화 요구 문구 제거(두 형식 모두)
- 회귀 테스트 8건 — 상수가 아니라 **조립된 프롬프트**를 검사(배선이 끊겨도 통과하는
  테스트를 만들지 않기 위해), 예화 요구 문구의 부활을 차단

지시문은 "예화를 쓰지 마라"가 아니라 **"지어내지 마라"**이다 — 참고 자료에 실제로
있는 예화는 출처를 밝히고 쓸 수 있다.

**남은 권고(별건):** 설교 경로도 `_GROUNDING_DIRECTIVE` 수준의 근거 강제를 받아야
한다. 다만 이는 생성 출력 전반을 바꾸므로 groundedness 베이스라인 재측정을 동반해야
하며, 본 작업 범위에 넣지 않았다.

### 5.2 적용 / 소그룹 질문 — 생성하되 검증한다

표준 기능이라 생성이 맞다. 다만 DBMA는 두 겹의 검증을 이미 갖고 있다.

```
설교 원고 + candidate TSU
  → 생성 (SermonDraftService 패턴 재사용, 전용 프롬프트)
  → doctrine_check()          # 기존 — 경고 전용, 생성 차단 안 함
  → judge_sermon_groundedness(text_type="application")   # 기존 — 인자만 바꿔 재사용
  → 점수와 함께 제시
```

`judge_sermon_groundedness()`는 이미 `text_type` 파라미터를 받는다
(`core/evaluation/sermon_judge.py`). 신규 개발이 거의 없다.

### 5.3 강단 전달 모드 — 가장 싼 승리

Sermonary의 Podium Mode는 **LLM이 전혀 필요 없다.** 저장된 원고를 큰 글씨·고대비로
렌더링하고 대지 단위로 넘기는 화면일 뿐이다.

artifact만 있으면 순수 렌더링이며, 실패할 여지가 없고 모델도 호출하지 않는다.
**투입 대비 효과가 가장 크다.** Streamlit로 충분하다.

### 5.4 재활용 — 범위를 정직하게 좁힌다

Pulpit AI의 핵심은 **설교 영상**에서 클립을 뽑는 것이다. DBMA에는 영상 입력이
없으므로 그 기능은 만들 수 없다(§7).

만들 수 있는 것: 원고에서 파생되는 텍스트 자산.

| 파생물 | 방식 |
|---|---|
| 주보용 요약 (3~5줄) | 생성 + groundedness |
| 소그룹 나눔지 | §5.2 재사용 |
| 묵상 카드 (대지별 1문장) | 생성 |
| 블로그 글 | 생성 + 원 설교 링크 |

SNS 자동 게시는 하지 않는다 — 외부 발행은 목회자 본인이 결정할 일이다.

### 5.5 시리즈 / 캘린더 — artifact 위에 얇게

artifact가 쌓이면 시리즈는 **메타데이터 한 줄**(`series_id`, `order`)로 성립한다.
캘린더는 `created_at` + 설교 예정일 필드의 목록 뷰다.

`sermon_corpus/analyzer/`(frequency, book_themes)를 그대로 돌려 **"최근 2년간
로마서만 12번 설교했습니다"** 같은 화면을 만들 수 있다 — 상업 제품의 캘린더보다
목회적으로 유용하다.

팀 협업은 로컬 아키텍처에서 파일 공유 수준까지만 가능하다(§7).

### 5.6 되먹임 — 이 설계의 진짜 값어치

```
생성된 설교 (artifact)
   → save_sermon_record() 로 RAW/설교_분리/ 에 .md 저장   # 기존 함수 재사용
   → 기존 처리 파이프라인이 다른 문서와 똑같이 처리
   → doc_type="설교" 로 분류 (2026-09-15 키워드 작업)
   → 설교 코퍼스에 편입
        ├─ 문체 참고 (_build_style_examples 가 여기서 읽도록 전환)
        ├─ 예화 검색 대상 (§5.1 — 한국어 예화 확보 경로)
        └─ 통계 (analyzer — 본문 편중·주제 반복 경고)
   → 다음 설교의 입력
```

`save_sermon_record()`의 docstring은 이미 이 의도를 적고 있다 — *"새 인제스트 경로를
만들지 않고 기존 흐름을 재사용"*. 지금은 **과거 설교 업로드**에만 쓰이는 이 경로를
**생성물**에도 연결하면 루프가 닫힌다.

현재 `_build_style_examples()`는 TSU 엔진의 임의 파일에서 400자씩 읽는다
(`sermon_draft.py:471`). 자기 설교 코퍼스에서 읽도록 바꾸면 ADR-032 SESAME의
Style Engine 슬롯에 실질적으로 진입한다 — SESAME 본안을 착수하지 않고도.

## 6. 단계 계획

우선순위는 **(매트릭스 이동량) ÷ (투입)** 기준이다.

| 단계 | 내용 | 해소되는 행 | 투입 | LLM |
|---|---|---|---|:-:|
| **P1** | SermonArtifact 저장·조회 | (기반) | 중 | 없음 |
| **P2** | 강단 전달 모드 | 강단 모드 | **소** | 없음 |
| **P3** | 예화 검색 | 예화 (→우위) | 중 | 없음 |
| **P4** | 적용·소그룹 질문 | 적용/질문 | 소 | 사용 |
| **P5** | 되먹임 (artifact → 코퍼스) | (전체 품질) | 소 | 없음 |
| **P6** | 재활용 텍스트 파생 | 재활용(부분) | 중 | 사용 |
| **P7** | 시리즈·통계 뷰 | 시리즈(부분) | 중 | 없음 |

P1~P3까지만 해도 **LLM 호출 없이** 매트릭스 3행이 움직인다. P2는 렌더링뿐이라
하루 작업이고 실패 위험이 0이다.

**선행 조건:** 인용 메타데이터(⚠️ 행)가 사이드카 결정으로 해소되어야 §5.1의
예화 출처 표시가 의미를 갖는다. C1 재요청 회신 대기 중.

## 7. 하지 않을 것 — 정직한 범위

| 항목 | 이유 |
|---|---|
| **설교 영상 클립** (Pulpit AI 핵심) | 영상 입력이 없다. 흉내내면 조악해진다. ❌로 남긴다 |
| **SNS 자동 게시** | 외부 발행은 목회자 결정. 초안까지만 |
| **실시간 팀 협업** | 로컬 아키텍처의 구조적 한계. 파일 공유까지 |
| **SaaS 전환** | 1인 개발·저작권·운영비. `NAE_FREE_DISTRIBUTION_PLAN_v1.md` 결론 유지 |
| **예화 LLM 생성** | **HQ 절대 규칙**(§5.1). 검색 0건은 정상 종료이며 생성으로 폴백하지 않는다 |

유통 형태(❌)는 **의도된 트레이드오프**로 재정의한다 — 설교 원고가 기기 밖으로
나가지 않는다는 것은 목회자에게 실질적 가치다. 상업 제품은 이 보장을 할 수 없다.
