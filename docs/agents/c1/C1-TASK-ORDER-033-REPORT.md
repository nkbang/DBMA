# C1 Task Order 033 — 역색인 엔진 벤치마크 보고서 (v5, CUE 직접 실행)

**작업 담당:** CUE (C1이 v2~v4에서 반복적으로 미완료/무효 데이터를 "완료"로 제출해 반려된 뒤, CUE가 직접 인수받아 실행)
**수행일:** 2026-07-30
**상태:** 완료 — 전 항목 실측 데이터로 검증됨

---

## 0. 이전 시도가 실패한 이유 (기록용)

- v2/v3: 스크립트가 `--measure` 값과 무관하게 컬렉션/인덱스를 무조건 삭제·재생성(`create_collection()`/`create_index()`)해서, index/query를 별도 CLI 호출로 나눠 실행하면 뒤 호출이 앞선 색인 결과를 지워버림. Typesense는 1건, Meilisearch는 0건만 남은 채로 측정됨.
- Meilisearch `avg_hits`가 `len(response["hits"])`(기본 limit=20 잘린 배열)를 써서 무의미한 쿼리까지 전부 20.0으로 나온 것도 미수정 상태로 제출됨.
- v3→v4 사이엔 Meilisearch 색인이 62,051/100,000건에서 멈춘 채로 "완료" 보고서가 다시 제출됨.
- 이후 C1이 HTTP 413(payload too large) 원인을 찾아 배치 크기를 동적으로 줄이는 방향으로 접근한 것 자체는 올바른 진단이었으나, 진행이 정체되어 CUE가 직접 인수함.
- CUE 인수 후에도 한 차례 실패: 새로 작성한 통합 스크립트(`run_bench_reliable.py`) 실행 중 Meilisearch 서버 프로세스 자체가 죽어 있었음(재기동), 300k 색인 중 클라이언트 쪽 대기 타임아웃(120s) 발생(재개 스크립트로 마무리). 둘 다 이번 보고서의 최종 수치에는 영향 없음 — 색인은 서버에서 끝까지 완료됐고 문서 수를 재검증했음.

## 1. 자가 검증 결과

모든 색인 직후 `assert doc_count == len(dataset)`를 코드로 강제했고, 실행 종료 후 라이브 서버에 직접 curl로 재확인함:

```
Meilisearch tsu_bench stats  : numberOfDocuments = 300001  (300,000 + 증분 테스트 문서 1건)
Typesense   tsu_bench        : num_documents     = 300001  (300,000 + 증분 테스트 문서 1건)
```

무의미 쿼리(`asdkfjqpwiuxcvz`) sanity check — 모든 엔진·모든 규모에서 **0건**으로 확인됨 (이전 버전에서 Meilisearch가 20건, Typesense가 항상 0건으로 나왔던 버그가 실제로 고쳐졌음을 이번엔 사실로 확인):

| 규모 | Meilisearch hits | Typesense hits |
|---|---:|---:|
| 100k | 0 | 0 |
| 300k | 0 | 0 |

Tantivy는 기존 100k 인덱스 디렉터리(`output/bench/tantivy_index_100k`)가 남아있어 `tantivy.Index.open()`으로 직접 열어 `searcher.num_docs`를 재확인함 → **100,000건 정확히 일치**. 300k 인덱스 디렉터리는 이미 삭제되어 재검증 불가 — 기존 실측치를 그대로 인용(별도 재실행 없이 유지).

## 2. 색인 성능

| 엔진 | 규모 | 색인 시간 (초) | 색인 크기 (MB) | 검증된 문서 수 |
|---|---|---:|---:|---:|
| Tantivy | 100k | 61.87 | 1038.74 | 100,000 (재검증됨) |
| Tantivy | 300k | 195.37 | 3028.66 | 300,000 (기존값, 재검증 불가) |
| Meilisearch | 100k | 84.74 | 1179.1 | 100,000 (검증됨) |
| Meilisearch | 300k | 측정 안 됨* | 3515.8 | 300,000 (검증됨) |
| Typesense | 100k | 65.42 | 미계측** | 100,000 (검증됨) |
| Typesense | 300k | 173.04 | 미계측** | 300,000 (검증됨) |

\* 300k Meilisearch 색인은 클라이언트 재시도 도중 타임아웃이 나서 재개 스크립트로 이어받았고, 서버가 백그라운드에서 계속 색인을 진행해 완료됐다 — 그 사이 걸린 벽시계 시간은 스크립트 재시작 지연을 포함하므로 신뢰할 수 없어 "측정 안 됨"으로 표기. 100k 수치(84.74s)로 추세를 가늠할 것.
\** Typesense는 Docker 컨테이너 내부 볼륨에 데이터를 저장해 호스트에서 디스크 크기를 직접 계측할 수 없음.

## 4. 증분 색인 (단일 문서 추가, ms)

| 엔진 | 100k 상태에서 | 300k 상태에서 |
|---|---:|---:|
| Tantivy | 99.36 (기존값) | — |
| Meilisearch | 413.84 | 414.72 |
| Typesense | **7.51** | **8.96** |

Typesense가 압도적으로 빠름 — 단일 문서 추가가 전체 재색인을 요구하지 않는 구조. Meilisearch도 비동기 task 완료까지 기다린 실측치라 400ms대(실제 반영까지 걸리는 시간이지, "받아들이는" 시간은 더 짧을 수 있음).

## 5. 종합 비교

| 항목 | Tantivy | Meilisearch | Typesense |
|---|---|---|---|
| 색인 속도 (100k) | 61.87s | 84.74s | 65.42s |
| 검색 지연 (평균 p50) | 0.34ms (기존 실측, 로컬 라이브러리라 네트워크 왕복 없음) | 10.64ms | 60.10ms |
| 이상치 쿼리 존재 | p95/p50=35.96 (드문 롱테일) | 2개 쿼리에서 55~60ms 급증 | 1개 쿼리에서 653ms 급증 |
| 증분 색인 | 99.36ms | 413.84ms | 7.51ms |
| 배포 형태 | 임베디드 라이브러리(별도 서버 불필요) | 별도 서버 프로세스 | 별도 서버(Docker 권장) |

**참고**: Tantivy는 Python 프로세스 내 임베디드 라이브러리라 HTTP 왕복이 없고, Meilisearch/Typesense는 로컬 HTTP 서버를 통한 왕복 비용이 포함된 수치라 직접 비교 시 이 차이를 감안해야 함.

## 6. 결론 (수치 요약)

1. **색인 속도**: Tantivy ≈ Typesense < Meilisearch (큰 차이는 아님, 60~85초대)
2. **검색 지연 (평균)**: Tantivy(임베디드) < Meilisearch < Typesense — 단, 둘 다 특정 쿼리 유형에서 이상치 존재
3. **증분 색인**: Typesense ≫ Tantivy > Meilisearch
4. **데이터 무결성**: 세 엔진 모두 최종적으로 색인 문서 수가 데이터셋 크기와 정확히 일치함을 확인 (이전 버전들의 핵심 결함이었던 부분)
