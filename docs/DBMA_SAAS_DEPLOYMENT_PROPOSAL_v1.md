**작성일:** 2026-09-15
**성격:** 전략·아키텍처 제안 — 실행 전 HQ 결정 필요
**전제:** 2026-09-15 베타 리셋 완료 상태 (코퍼스 빈 상태 = SaaS 설계에 유리한 출발점)

## 0. 결론 먼저

SaaS 전환의 난점은 서버를 구하는 일이 아니라 **"무엇을 파는가"를 먼저 정하는 일**이다.
현재 코드는 *한 명의 목회자가 자기 장서로 자기 컴퓨터에서 쓰는 것*을 전제로 짜여 있고,
그 전제가 아키텍처 곳곳에 박혀 있다(§2). 그리고 기존 코퍼스는 상용 전자책이라
**서버에 올리는 순간 배포 행위가 된다**.

권장 방향:

> **"목회자가 자기 장서를 올려 쓰는 개인 서재 SaaS"** + **퍼블릭 도메인 NAE 코퍼스 기본 제공**

이 구조는 세 문제를 동시에 푼다.
- 저작권 — 사용자가 자기 소장본을 올리고, 공용 제공분은 퍼블릭 도메인만
- 메모리 — 테넌트당 코퍼스가 작아 §2-1의 치명적 제약이 자연 해소
- 차별화 — Logos가 못 하는 "내 서재 + 내 설교 문체"가 상품성의 핵심

## 1. 무엇을 파는가 — 세 가지 선택지

| | A. 개인 서재형 | B. 공용 코퍼스형 | C. 하이브리드 **(권장)** |
|---|---|---|---|
| 코퍼스 | 사용자 업로드 | NAE 퍼블릭 도메인 | 양쪽 |
| 저작권 | 사용자 책임(단, 서버 보관은 회색지대 — §5) | 완전 무결 | 관리 가능 |
| 초기 가치 | 업로드 전까지 빈 깡통 | 즉시 사용 가능 | 즉시 + 개인화 |
| Logos 대비 | 우위(내 장서) | 열세(콘텐츠 규모) | 우위 |
| 구현 난이도 | 높음(테넌시) | 낮음 | 높음 |

**C를 권하는 이유:** B만으로는 Logos·Sermonary와 콘텐츠 규모 싸움이 되는데 이길 수 없다.
A만으로는 가입 직후 아무것도 못 한다. NAE 코퍼스(Fuller 8권·Dagg·Hiscox·Smith 4권·신앙고백서)를
기본 탑재해 첫날부터 쓰게 하고, 자기 장서를 올리면 그때부터 대체 불가능한 도구가 된다.

## 2. 현재 아키텍처가 SaaS를 막는 지점 (VERIFIED)

### 2-1. 세션마다 전체 코퍼스를 메모리에 적재 — **가장 치명적**

`RetrievalEngine.__init__()`이 `_load_corpus()`로 TSU 전량을 메모리에 올리고
(`core/retrieval.py:1414`), 이 엔진은 **브라우저 세션당 1개** 생성된다
(`ui/state/query_processor.py` — `st.session_state["shared_query_processor"]`).

코드 주석에 실측치가 남아 있다(`core/retrieval.py:1420`): TSU당 **4.81 KB**,
TF-IDF 폴백까지 켜지면 **19.1 KB**.

| 동시 사용자 | 90,000 TSU 기준 메모리 |
|---|---|
| 1명 | 0.4 GB (폴백 시 1.7 GB) |
| 20명 | 8.6 GB (폴백 시 **34 GB**) |
| 100명 | 43 GB (폴백 시 **172 GB**) |

**공용 대형 코퍼스 + 멀티테넌트는 이 구조로 불가능하다.** 반대로 테넌트당 수천 TSU
규모의 개인 서재라면 감당 가능하다 — §0의 방향을 뒷받침하는 기술적 근거다.

### 2-2. 인증·테넌시 개념이 존재하지 않음

`ui/app.py`·`core/config.py`에 `login`/`auth`/`user_id`/`tenant`/`session_id` **0건**.
모든 방문자가 같은 registry·같은 TSU 데이터셋·같은 업로드 폴더를 공유한다.
지금 상태로 공개하면 **A 목사의 설교 원고를 B 목사가 본다.**

### 2-3. 파일 기반 단일 레지스트리 + 파일락

`registry_lock()`(`core/identity_registry.py:43`)이 프로세스·스레드 간 직렬화를 담당한다.
공유 파일시스템 전제이므로 **인스턴스를 늘려도 수평 확장이 되지 않고**, 오히려 락 경합만 는다.
`background_index_builder`가 5초 주기로 같은 파일을 쓰는 구조(`interval_seconds=5.0`)라
인스턴스가 2개면 서로의 쓰기를 덮는다.

### 2-4. 로컬 Ollama 종속

임베딩 `bge-m3:latest`, 생성 `my-theology-bot-v2`/`llama3.1:8b`, groundedness judge
`dbma-planner-r1-q6:70b`. **70B 모델을 상시 GPU에 올려두는 비용**이 SaaS 원가의 대부분을
차지하게 된다.

### 2-5. Streamlit 실행 모델

상호작용마다 스크립트를 재실행하고 무거운 객체를 `session_state`에 캐시하는 구조다.
데모·내부 도구로는 훌륭하지만 멀티테넌트 제품 런타임으로 설계된 물건이 아니다.

### 2-6. 부차적이지만 실무에서 걸리는 것

- `Dockerfile` 부재 (Qdrant용 compose만 존재)
- `hunspell` 네이티브 의존성 — Apple Silicon 설치 이슈가 requirements 주석에 기록돼 있음
- 파일 경로가 `data/RAW`·`data/제련완성본` 등 로컬 상대경로 전제

## 3. 단계별 방안

### Phase 0 — 관리형 단일 테넌트 파일럿 (권장 시작점)

**아키텍처를 거의 바꾸지 않고** 목회자 5~10명에게 **1인 1인스턴스**를 제공한다.
컨테이너 하나 = 사용자 하나 = 데이터 완전 격리.

- Dockerfile 작성 (앱 + Ollama 사이드카 또는 외부 LLM API)
- 사용자별 볼륨 분리, 리버스 프록시 + 기본 인증
- 인스턴스당 메모리 상한 설정 (§2-1 근거로 산정)

**얻는 것:** 테넌시를 구현하지 않고도 진짜 사용자 피드백과 과금 의사를 검증한다.
**한계:** 사용자당 원가가 높아 수십 명 이상으로는 못 간다 — 그게 이 단계의 목적이다.

> 이 단계에서 **가격을 받아보는 것**이 가장 중요하다. 경쟁 제품이 월 $39~99(Sermonary
> $49, Pulpit AI $39~129)이므로, 월 3~5만원에 결제하는 목회자가 5명 나오면 Phase 1의
> 투자 근거가 생기고, 0명이면 Phase 1을 하지 않는 것이 옳은 결정이다.

### Phase 1 — 멀티테넌트 기반 구축

Phase 0에서 수요가 확인된 경우에만 착수한다.

| 영역 | 현재 | 목표 |
|---|---|---|
| 인증 | 없음 | Clerk/Auth0 등 외부 IdP (직접 구현 금지) |
| 테넌시 | 없음 | 모든 데이터 경로에 `tenant_id` 강제 |
| 검색 | 메모리 전량 적재 | **Qdrant 테넌트별 컬렉션** — NAE에 이미 구현 자산 존재 |
| 레지스트리 | JSON 파일 + 파일락 | PostgreSQL |
| 원본 보관 | 로컬 디스크 | S3/R2 (+ 저장 시 암호화) |
| 임베딩 | 로컬 Ollama | 관리형 임베딩 API 또는 전용 GPU 1대 |
| 생성 | 로컬 Ollama | 호스팅 LLM API |
| judge 70B | 상시 | **비동기 배치** — 실시간 경로에서 분리 |

**ADR 충돌 주의:** System Charter의 *One Retrieval Engine*은 "전역 단일 인스턴스"로
읽히지만, 멀티테넌트에서는 *"엔진 구현은 하나, 인스턴스는 테넌트별"*로 재해석해야 한다.
**이건 새 ADR 없이 진행하면 안 된다**(CLAUDE.md Architecture Freeze Rule).

### Phase 2 — 상용화

- Streamlit → API 서버 + 웹 프론트 분리 (Phase 1까지는 Streamlit 유지 권장)
- 사용량 미터링·구독 결제
- 설교 전달 계층(강단 모드·소그룹 질문·예화) — 경쟁 제품 대비 결손 기능

## 4. 원가 구조와 가격

SaaS 원가를 지배하는 것은 서버가 아니라 **LLM 추론**이다.

- 설교 1편 = 개요 1회 + 대지 확장 3~5회 + judge 1회 ≈ **LLM 호출 5~7회, 긴 컨텍스트**
- 목회자는 주 1~2편 → 월 8~14편 → 월 40~100회 호출

**자체 GPU 상주**(70B judge 포함)는 사용자가 적을 때 원가가 폭발한다.
초기에는 **호스팅 LLM API 종량제**가 명백히 유리하고, 사용자가 충분히 늘어난 뒤
GPU 자체 운영을 재검토하는 순서가 맞다.

목표 가격은 경쟁 제품과 같은 대역(월 $39~59 / 5~8만원)이 현실적이다. 한국 목회자
시장은 이 가격 저항이 미국보다 크므로, **Phase 0에서 실제 결제 의사를 반드시 확인**해야 한다.

## 5. 법적 경계 — 가장 먼저 정리해야 할 항목

| 항목 | 판단 |
|---|---|
| 기존 상용 전자책 코퍼스를 서버에 탑재 | **불가** — 배포 행위 |
| NAE 퍼블릭 도메인 코퍼스 제공 | 가능 |
| 사용자가 자기 소장본을 업로드 | 조건부 — 약관에 권리 보증 조항 필수, 사용자 간 공유 차단 필수 |
| 업로드 원문을 그대로 반환 | 인용 분량 제한 필요 |
| 설교 원고 서버 보관 | 목회 상담 내용이 섞이므로 **민감정보 취급** — 암호화·보존기간·삭제권 명시 |

설교 원고는 단순 문서가 아니다. 교인 실명·가정사가 예화로 들어가는 경우가 흔하다.
**로컬 실행의 프라이버시 우위를 스스로 포기하는 것이 SaaS 전환의 최대 비용**이며,
이를 상쇄할 만큼의 편의를 제공하지 못하면 전환할 이유가 없다.

## 6. 권고 — 솔직한 판단

**지금 바로 Phase 1(멀티테넌트)에 들어가는 것은 권하지 않는다.** §2의 제약은 개별로는
해결 가능하지만 전부 합치면 사실상 재작성에 가깝고, 그 투자를 정당화할 수요가 아직
검증되지 않았다.

우선순위는 이렇게 본다:

1. **Phase 0 파일럿으로 수요와 가격을 검증** (수 주)
2. 병행해서 **NAE 퍼블릭 도메인 코퍼스를 제품 수준으로 완성** — SaaS든 패키지든
   법적으로 깨끗한 콘텐츠는 어느 경로에서도 필요하다
3. 결제 의사가 확인되면 Phase 1 착수, 확인되지 않으면 **설치형 배포 패키지**로 방향 전환
   (`scripts/build_mac_package.sh`가 이미 있고, `beta-v1.3.0-rc5` 태그까지 나와 있다)

설치형 패키지는 SaaS의 하위 호환이 아니라 **다른 상품**이다. 저작권 문제가 사라지고,
프라이버시가 유지되며, 원가가 0에 수렴한다. 목회자 시장에서는 이쪽이 더 맞는 답일
가능성이 실제로 있다.
