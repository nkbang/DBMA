## 1. 배경

Design Brief는 P0(홈/내비게이션/검색/도움말/Sample Library) 5개만
공식 정의했고, "P1/P2"는 실행계획 문서의 자리표시자였을 뿐 실제 목록은
없었다. 이번에 Stitch 목업과 라이브 앱을 대조해 P1을 아래처럼 새로
확정한다 — **UX-002 때처럼 기술 용어 grep 감사는 이미 1차로 돌려
research.py/sermon_draft.py에서는 추가 위반이 발견되지 않았다.** 이번
Task는 잔여 항목(§5.2 나머지 체크리스트, 구조 확인)에 집중한다.

## 3. 확인 필요 — "자료 읽기" 화면의 실제 위치

`document_reading.html` 목업에 대응하는 독립된 `ui/pages/*` 파일이
존재하지 않는다. 착수 전 아래를 확인한다.

- Library 문서 상세 패널(`_render_document_detail_panel`,
  `ui/pages/library.py`)이 이 역할을 흡수하고 있는가?
- 아니면 Research 캔버스 안에서 문서를 펼쳐보는 흐름이 이 역할을
  대신하는가?
- 둘 다 아니라면 실제로 빠진 화면인가(향후 별도 구현 필요)?

이 중 하나로 확인되면 그에 맞춰 §4 범위를 조정한다 — 새로 화면을 만드는
작업이 아니라면 범위에서 제외.

**확인 결과 (2026-07-31)**: 어디에도 흡수되어 있지 않음 — Library 상세
패널은 메타데이터만, Research는 짧은 발췌만 표시. 처리된 문서 본문
전체를 읽는 기능이 라이브 앱에 전혀 없는 진짜 기능 공백으로 확인됨.
새 Task Order로 분리 발행: [DBMA-UX-005-DOCUMENT-READING-PLAN.md](DBMA-UX-005-DOCUMENT-READING-PLAN.md).
본 문서(UX-004)는 나머지 3화면(연구하기/설교 준비/온보딩)만 계속 진행.

## 4. 점검 항목 (화면당 동일하게 적용)

Design Brief §5.2 체크리스트 중 지금까지 다루지 않은 항목들:

- [ ] 각 화면에 "다음 행동" 버튼이 있는가(Dead End 없음)
- [ ] 빈 상태(empty state)가 있다면 Sample 데이터 또는 안내로 채워지는가
- [ ] 목업과 비교해 정보 계층(제목 → 본문 → 행동)이 크게 어긋나지 않는가
      — 목업 그대로 재현하라는 뜻이 아니라, 사용자가 다음에 뭘 할지
      알 수 있는 구조인지 확인
- [ ] 브랜드(내서재/NAE) 일관성 — 이미 이 3화면은 통과했지만 재확인

## 8. 실제 감사 결과 — grep으로 못 잡은 동적 문자열 위반 다수 발견

당초 §2의 1차 grep 감사(리터럴 문자열만 검색)는 통과했지만, **브라우저로
실제 검색을 실행해보니 f-string으로 동적 생성되는 문자열에서 grep이
못 잡은 위반이 다수 발견됐다** — 이번 Task의 가장 중요한 교훈이다.

### research.py (연구하기) — 발견 즉시 수정

| 위치 | 위반 | 수정 |
|---|---|---|
| 검색 옵션 | "검색 방법" 드롭다운에 `Hybrid/BM25/Vector/RRF` 알고리즘명 그대로 노출, "최소 점수" 슬라이더 | `NAE_ADMIN_MODE` 게이트, 일반 사용자는 기본값(Hybrid, 0.0) 고정 |
| 결과 카드 | `RRF {score:.4f}` 배지 (알고리즘명+원시 점수) | 별점(⭐)으로 단순화 |
| 결과 카드 | `doc_type`이 항상 "TSU"(내부 코퍼스 포맷명)로 표시 | 표시 자체를 제거 |
| 결과 제목 | `book_id` 원시 코드(`ROM 8:1-4`) | `core/sermon/bible_books.py` 매핑으로 한글 변환(`로마서 8:1-4`) |
| 검색 분석 | `intent.upper()`로 영어 enum 그대로(`EXEGESIS` 등) | 한글 라벨 매핑(본문 해석/비교/묵상/신학적 고찰/관련 구절) |
| 검색 분석 | "감지된 성서 도서"에 `ROM` 등 원시 코드 | 한글 성경 이름 변환 |
| 전반 | "쿼리"(영어 차용어) 다수 — 섹션 제목/버튼/안내 문구 | "검색어"/"검색"으로 통일 |
| 결과 정렬 | `["relevance", "date", "title"]` 영어 옵션 | `["관련도순", "날짜순", "제목순"]` |
| 에러 메시지 | `"TSU 데이터셋을 찾을 수 없습니다"` | `"자료를 찾을 수 없습니다"` |
| 결과 제목 fallback | `"미제시"`(어색한 표현) | `"제목 없음"` |

### sermon_draft.py / onboarding.py

같은 방식(동적 문자열 패턴 grep + 코드 리뷰)으로 재점검 — 추가 위반 없음.

### 교훈

리터럴 문자열 grep 감사(UX-002에서 쓴 방식)는 `st.markdown(f"...{var}...")`
형태로 런타임에 조합되는 문자열을 놓친다. **화면에 실제 데이터가 들어간
상태로 브라우저에서 확인하는 절차가 없으면 이런 위반은 코드 리뷰만으로
못 잡는다.** 향후 UX 감사는 정적 grep 이후 반드시 실 데이터로 브라우저
검증을 거칠 것.
