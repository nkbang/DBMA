# J4 — 본문 지정 질의 경로 (2026-10-18)

J0에서 `verse_mapping.book_id` 보유율이 **0.0%**로 측정됐다. 목회자의 1순위
사용 패턴이 본문 지정 질의("로마서 8:1-4…")이므로, 계획 단계에서는 이것을
⑤의 하드 블로커 후보로 올렸다. 단 **추정 금지** 원칙에 따라 "복구가 필요한가"
부터 측정하기로 했다(계획서 J4: 이득이 입증되면 승인 요청, 입증 안 되면
착수하지 않고 기록으로 닫는다).

## 1. book_id는 왜 비어 있었나 — 버그가 아니라 설계 전제

`core/tsu_builder.py` 빌드 시점 게이트:

```python
book_id = _resolve_book_id(source_file)   # ← 파일명에서 뽑는다
if book_id != "UNK":
    verse_mapping["book_id"] = book_id
    ref, provenance = _resolve_evidence(content, book_id)
    if ref is not None and ref.book_id == book_id:   # 문서 책과 일치할 때만
        verse_mapping["chapter"] = ref.chapter
        ...
```

`book_id`는 **파일명**에서 결정된다 — "문서 1권 = 성경 1책"(주석서) 전제다.

| 자료 | 파일명 | book_id | 결과 |
|---|---|---|---|
| 영문 설교집 67종 | `Spurgeon_MTP_Vol30.txt` | **UNK** | `verse_mapping` 전체가 빈 `{}` |
| 한국어 5종(J5) | `3. 마가복음.pdf` | **MRK** | book_id + chapter/verse까지 채워짐 |

그래서 영문 청크의 TSU id가 전부 `TSU-UNK-…`로 시작한다. 본문에
"Romans 8:1"이 있어도 파일명이 책을 가리키지 않으면 채워지지 않는다.
STATE.md 2026-09-18 기록("book_coverage 24/66 미달은 버그 아님 — 1권 전담
주석서가 많은 콘텐츠 구성 특성")과 정합한다.

**"복구"라는 개념이 성립하지 않는다** — 과거에 있었다가 사라진 값이 아니다.
새로 만들려면 파일명 전제를 버리고 **청크 본문 기반 추출**로 설계를 바꿔야
하며, 그것은 ADR-030 / TSU Pipeline 변경이다.

## 2. J5의 부수 효과 — 자료를 넣으면 book_id가 따라온다

| 항목 | J5 전 | J5 후 |
|---|---:|---:|
| book_id 보유 청크 | 0건 (0.00%) | **1,995건 (1.64%)** |
| 등장 성경 책 | 0 | 3 (ACT 828 · JHN 761 · MRK 406) |
| `bible_index` 포스팅 | **0행** | **9,995행** |

한국어 자료 5종이 **전량**(1,995/1,995) book_id를 가졌다. 성경공부 교재라
파일명이 책을 가리키고, 본문도 "요한복음 3:16" 형태로 장절을 명시한다.

그 결과 `bible route`(정확 참조 매칭)가 살아났다. 실측:

```text
"요한복음 3:16의 핵심 메시지는 무엇입니까?"
  → book_id=JHN · chapter=3   모든 사람을 위한 요한복음 I부 (1-10장)
  → book_id=JHN · chapter=3   (동일)
  → book_id=JHN · chapter=3   (동일)

"로마서 8:1-4은 … 정죄 없음에 대해 무엇을 말합니까?"
  → book_id 없음 · 영문 Spurgeon 5건 (자유 텍스트 폴백)
```

즉 **book_id가 있으면 장 단위 정밀도**가 올라가고, 없으면 자유 텍스트로
보정된다. 이득은 실재하지만 그 이득은 **자료를 넣으면 자동으로 따라온다** —
별도 "복구 작업"이 아니라 J5의 연장선이다.

## 4. 왜 0%인데도 작동하는가 — 이미 두 겹의 보정이 있다

2026-09-26에 들어간 두 수정이 book_id 공백을 전제로 설계돼 있다
(`core/hybrid_candidate_pipeline.py`):

1. **`_corpus_has_book_ids()`** — 코퍼스에 book_id가 없으면 `book_ids` term
   필터(`Occur.Must`)를 **애초에 얹지 않는다**. 이 보정 전에는 "책 이름이
   들어간 모든 질의가 구조적으로 0건"이었다(실측: `no condemnation in Christ
   Jesus` → 2건 vs `Romans no condemnation…` → 0건).
2. **bible route 폴백** — 포스팅 리스트가 비면 자유 텍스트 검색으로 내려간다.

여기에 한국어 질의 번역(`core/query_translation.py`)이 책 이름을 영어로
바꿔 BM25에 얹으므로, 영문 코퍼스에서도 본문 질의가 매칭된다.

## 5. 이득 상한 — 설계를 바꿔도 5.4%

영문 코퍼스 119,595 청크의 성경 참조 표기 분포(실측):

| 표기 | 건수 | 비율 | 추출기 인식 |
|---|---:|---:|---|
| 아라비아숫자형 `Romans 8:1` | 433 | 0.4% | ✅ (단 파일명 게이트에서 탈락) |
| **로마숫자형 `Romans viii. 28`** | **4,592** | **3.8%** | ❌ |
| 약어형 `Rom. 8` | 1,399 | 1.2% | ❌ |

추출기 실측(`_resolve_scripture_ref`):

```text
"Romans 8:1"        → ROM 8:1     ✅
"Romans viii. 28"   → None        ❌  ← 영문 자료의 주류 표기
"Rom. 8:1"          → None        ❌
"로마서 8:1"         → ROM 8:1     ✅
"John xvii. 3"      → None        ❌
```

로마숫자·약어 파서를 추가하고 파일명 게이트까지 본문 기반으로 바꿔도
**상한은 약 5.4%(6,400건)**다. 그리고 그 이득이 검색에 반영되는 경로는
bible route 포스팅뿐인데, 그 route는 §4처럼 이미 폴백으로 보정돼 있다.

## 6. 하지 않는 이유 — 이득은 작고 위험은 실측된 적이 있다

설교문 한 청크에는 여러 책의 참조가 섞인다. 본문 기반 추출로 book_id를
채우면 오분류가 생기고, 그러면 `_corpus_has_book_ids()`가 `True`로 바뀌어
**`book_ids` term 필터가 다시 켜진다** — 잘못된 필터는 `Occur.Must`라서
0건을 만든다. 이것이 2026-09-26에 실측된 사고 패턴이다("책 이름이 들어간
모든 질의가 구조적으로 0건"). 빌드 시점 게이트에 "문서 책과 일치할 때만
chapter/verse를 채운다"는 조건이 붙은 이유도 같다(전수 실측 64.88% 불일치).

검증되지 않은 분류기 위에 다중 처리 경로를 얹지 않는다는 원칙과도 맞지
않는다.

## 7. 판정

**게이트 G4 — 이득 미입증 → J4 CLOSED (결함 아님).**

- book_id 0%는 버그가 아니라 "파일명 = 1책" 설계 전제의 결과다.
- 그 상태에서도 본문 질의 회수는 **85.7% 적중**, 하드 유보 0건, 0.2~3.2초.
- book_id의 이득(장 단위 정밀도)은 실재하지만 **자료를 넣으면 자동으로
  따라온다**(J5 한국어 5종이 1,995건 전량 공급, `bible_index` 0행 → 9,995행).
- 설계를 바꿔 영문 자료에서 뽑아내는 쪽은 상한 5.4%에 오분류로 0건을 만들
  위험이 실측돼 있어 **권고하지 않는다**.
