## 2. 가장 중요 — 코퍼스가 두 트랙으로 갈라져 있다 (읽어야 함)

### 2.1 무슨 일이 있었나

`~/DBMA`(이 세션 내내 "프로덕션"으로 다룬 실제 앱 경로)의
`output/bench/tsu_dataset.jsonl`은 지금 **130,401건 / 67개 출처**이고, 전부
archive.org 퍼블릭 도메인 영문 자료(Spurgeon·Maclaren·Whitefield·Broadus·
Dargan·Keach·Hovey)뿐이다. 조직신학·주석·한글 자료가 **하나도 없다.**

그런데 메모리(`project_corpus_recovery_cancelled.md`, 2026-09-18 최종 수정)는
프로덕션 코퍼스가 **84,766건 / 125개 출처**(Dagg·Fuller 8권·Hiscox·NICNT류·
한글 로마서/고린도전후서 포함)라고 기록하고 있다. P0-5 대표 질의 24건(비교
신학·목회 상담 유형 다수 포함)도 이 84,766건 상태를 가정하고 설계됐다.

**확인한 사실(backups/ 폴더 실측)**:
- `backups/pre_nontheo_removal_20260918/tsu_dataset.jsonl.89836` — Track A
  복원 직후 스냅샷(89,836건, 신학무관 제거 전)
- `backups/pre_recovery_20260918/tsu_dataset.jsonl.spurgeon_119595` —
  **"spurgeon"이라고 명시적으로 라벨링된** 119,595건 스냅샷. 지금 프로덕션
  상태(67종 베이스라인)의 직계 조상.

라벨("spurgeon_119595")과 타이밍으로 볼 때, 이건 사고가 아니라 **의도적으로
Track A(연구용 125종 코퍼스)를 백업해 두고 "동봉 서재"(배포용 67종 퍼블릭
도메인 최소 코퍼스, S2-3/S2-4 작업)로 전환한 것**으로 보인다. `docs/
RELEASE_ASSET_PROVENANCE.md`가 상업 주석·도서 스캔 다수를 "배포 불가"로
판정한 것과 방향이 일치한다 — Track A의 일부(Dagg·Hiscox는 CLEAN 판정
받았었지만)가 전부 배포 가능하다고 재확인된 상태는 아니었다.

**단, 이건 CUE의 추정이다 — 실제로 "동봉 서재로 전환"이 의도된 결정이었는지,
아니면 어느 세션에서 실수로 Track A 대신 옛 베이스라인 브랜치를 기준으로
작업을 이어간 것인지는 확인하지 못했다.** `NAE/corpus/`(2.6GB, "다른 세션이
지금도 작업 중"이라고 2026-09-15 이양 문서에 적혀 있음)에 Track A 콘텐츠가
따로 보존돼 있을 수도 있다 — 확인 안 함.

### 2.2 왜 중요한가

1. **데이터는 잃지 않았다** — Track A는 `backups/pre_recovery_20260918/`,
   `backups/pre_nontheo_removal_20260918/`에 온전히 남아 있다. 복원 가능.
2. **P0-5 "회귀"는 버그가 아니었다** — 자세히는 §3-3.
3. **다음 세션이 반드시 사용자에게 확인해야 할 것**: 실제 배포판(beta)이
   **의도적으로 67종 퍼블릭 도메인만** 담아야 하는 게 맞는지(법적으로
   안전한 최소 구성), 아니면 Track A(125종, 조직신학·주석 포함, 배포 가능
   여부 재검토 필요)를 다시 합치는 게 맞는지. **이 결정이 S6-2(P0-5 채점)·
   S6-3(외부 테스터가 실제로 만나는 코퍼스)·향후 배포 자산 구성 전체에
   영향을 준다.**

### 2.3 지금 당장 뭘 해야 하나 (다음 세션 착수 시)

1. 사용자에게 §2.2의 질문을 그대로 물어볼 것 — 추측해서 진행하지 말 것.
2. "67종 베이스라인이 맞다"고 하면: P0-5 채점 자료(이미 재수집함,
   `docs/NAE_GOLD_QUERY_SET_P0_5_RAW_ANSWERS_001.json`)를 그대로 쓰되,
   유보 응답 비율이 높은 건 **정상**이라고 사용자에게 안내(§3-3 참고).
3. "Track A를 다시 합쳐야 한다"고 하면: `backups/pre_recovery_20260918/
   tsu_dataset.jsonl.spurgeon_119595` 이전의 84,766건 상태

## 5. 함정 (다음 세션이 반복하지 말아야 할 것)

1. **`~/DBMA`가 "프로덕션"이라는 가정을 의심 없이 쓰지 말 것.** 이번
   세션 내내 그렇게 다뤘지만, §2에서 보듯 이 경로의 코퍼스 상태 자체가
   최근에 바뀌었을 수 있다. 코퍼스 관련 작업 전에는 `output/bench/
   tsu_manifest.json`의 `generated_at`·`source_document_count`부터
   확인할 것.
2. **`open_or_build_index()`의 staleness 감지는 레코드 개수만 본다.**
   내용이 바뀌어도 개수가 같으면 재빌드가 안 된다 — 코퍼스 파일을 in-place
   수정하는 작업(사이드카 백필 같은) 후에는 `output/bench/tantivy_index`를
   수동으로 지우고 재빌드할 것. 이번 세션 중 이걸 몰라서 "인덱스가 stale
   해서 그런가?"로 잘못된 가설을 한 번 거쳤다(실제 원인은 아니었음 —
   §3.3 참고).
3. **`p0_5_run_all.py`는 `RESULT_001.md`(사람이 읽는 문서)를 자동 갱신하지
   않는다** — `RAW_ANSWERS_001.json`만 새로 쓴다. RESULT 문서는 그 JSON을
   보고 수작업(또는 별도 스크립트)으로 다시 정리해야 한다.
4. 이 세션이 사용한 스트리밍/백그라운드 명령(`timeout 900 ... &`)은 정상
   동작했다 — 예전 메모리의 "`timeout` 명령 자체가 깨져 있다"는 기록은
   이번엔 재현되지 않았다(harness의 120초 자동 백그라운드화와 혼동하지
   말 것, 별개 메커니즘).
5. registry `documents.json`이 81→77로 변한 건 이번 세션이 한 일이
   아니다(별도 세션, §3.7) — 이번 세션의 사이드카 백필(PR #60) 작업은
   그 전에 이미 끝나 있었다.
